# 实况录制与离线成片设计

## 目标

不做直播推流。一场「AI 操作游戏 + 思考 + 解说」的过程要能完整留下，并在
事后生成带配音的 VTuber 视频。为此需要三件事：

1. 画面完整录制；
2. 思考、解说、模拟输入、VTuber 模型参数写进**一份可读文件**；
3. 语音后期生成，并按这份文件的时间轴对齐。

不追求实时性，也不要求录制时就有声音。声音、口型、字幕都以会话文件为
唯一时间基准。

## 分层

```text
BetterGI 实时会话（本机 WS）
        │  画面 / 指导 / 解说 / 动作状态 / 动作回显
        ▼
录制器 record_session.py
        │  gameplay.mp4 + session.jsonl
        ▼
后期渲染 render_session.py
        │  SAPI / SVC 配音 + ASS 字幕 + ffmpeg 合成
        ▼
final.mp4 + render.json
```

录制器是被动消费者：它不启动游戏、不操作游戏，也不产生解说。操作仍由
Lumine 桥通过 BetterGI 的模拟输入通道完成；导演 `live_director.py` 负责
思考与解说并写回同一实时会话。把录制器换成直播叠加层，就是原来的直播
形态；因此两套形态共用同一条数据链。

## 时间模型

* 录制起点 `t0`：第一条实时画面（或第一条事件）的 UTC 时间；
* 所有事件用 `t`（毫秒，相对 `t0`）记录，写入时即落盘；
* 画面从 `t=0` 开始编码；若画面晚于第一条事件，`video` 事件记录偏移，
  渲染器用 `tpad` 在片头补帧；
* 解说事件自带预估时长 `dur` 与口型包络；渲染器把实际音频用 `atempo`
  调到 `dur` 附近（0.75–1.5 倍），因此声音、字幕、口型共用一条时间轴。

`atempo` 的边界是刻意保守的：超出范围说明文本与语速差异过大，强行拉伸
会明显失真；此时保留原速并在 `render.json` 记警告，让人工决定是否改写
台词。

## 会话文件

`session.jsonl` 是唯一权威记录，格式见
[integrations/session/README.md](../../integrations/session/README.md)。
设计约束：

* 一行一个 JSON，UTF-8 无 BOM，不依赖任何二进制索引；
* 首行固定为 `session` 元信息，便于流式读取与损坏检测；
* 事件类型封闭；未知类型读取时报错，避免静默丢信息；
* `avatar` 事件使用 VTube Studio 参数 ID（`ParamMouthOpenY` 等），
  不绑定具体 Live2D 模型；
* 画面另存 MP4，但删除视频后会话文件仍然完整可解释。

## VTuber 参数

录制器生成三类参数：

| 操作 | 内容 | 生成方式 |
|---|---|---|
| `pose` | 头部/身体角度、呼吸、眼球位置 | 每秒一次的正弦慢摆 |
| `blink` | 眨眼，持续 120ms | 3.5–5.5 秒随机间隔 |
| `speech.avatar` | 表情、嘴型、眉毛、口型包络 | 由情绪与文本推导 |

口型包络在录制时就固定下来，后期只做音频时长匹配；这样「模型怎么动」
不依赖 TTS 引擎是否可用，也不会因为换引擎而丢失。

## 失败与恢复

* WebSocket 断开：录制器按指数退避重连，画面继续用上一帧保持时长；
* 画面源失败：会话文件照常写，`end` 事件与视频缺失可被渲染器识别；
* 录制进程被强杀：已写事件仍可读，`validate()` 会指出缺少 `end`；
* 渲染失败：`render.json` 记录每条配音的状态，`session.jsonl` 不被修改。

## 安全边界

整条链路只使用 BetterGI 已公开的画面截图与模拟键鼠接口；录制器不读写
游戏内存、不抓包、不注入进程、不执行游戏脚本。导演的 LLM 调用与 AutoDL
推理都在本机之外发生，会话文件只保存文本与时间，不保存令牌。
