## 0. 怎么读这份日志

**三条来源，优先级从高到低：**

| 来源标记 | 含义 | 处理方式 |
|---|---|---|
| 用户拍板 | 用户在本次问答中直接选择的选项或原话 | 不得擅自更改；要改必须先问 |
| 代码证据推导 | 从现有 `agent/` 代码读出的既成事实（行为、限制、已有能力） | 可作为实现前提，但允许被重构 |
| 设计新增 | 本设计为消解冲突而补的约定（schema、接口、阈值） | 可讨论；实现前应复核 |

**列义**：

- **编号**：`D01`–`D124`，按主题分组（A–J），全局唯一，供后续 issue / commit 引用。
- **主题**：所属子系统。
- **决策**：一句话，写成可直接落地的实现约束。
- **依据**：用户原话用「」括起；无原话时写问答轮次主题（如「问答轮次：快系统#1」）。不臆造 m-ref。
- **影响**：涉及文件/目录，或写「设计约束」。

**待定的写法**：决策列以「待定：」开头 = 方向已定、参数未定，缺什么见 §M。

## A. 快系统（Omni realtime）

要点（读表前先理解）：
- 快系统是**执行环节**，不是规划环节；全部使命是把一条意图做完。
- 与 GameScaling **并行**：一个看画面说话，一个出键位，互不等待。
- 每条意图**新建一个 realtime 会话**，结束即断——用冷启换上下文绝对干净。
- 输出协议是 **function call**，不靠自由文本正则。
- 上下文只保留**本意图执行过程**，跨意图靠交棒载荷衔接。
- 话语与动作共享**同一路画面**（gamescaling 侧截屏推流），避免"嘴说左、手按右"。

| 编号 | 主题 | 决策 | 依据 | 影响 |
|---|---|---|---|---|
| D01 | 角色 | 快系统 = 执行环节，并行跑 Omni realtime 与 GameScaling | 「他是执行环节，并行跑 omni-realtime 和 gamescaling 模型」 | `agent/executor.py`、`agent/omni.py` |
| D02 | 角色 | realtime 负责看画面、出解说、判断执行是否应结束 | 「realtime 负责看画面，给出解说，判断执行是否应该结束」 | `agent/fast_stream.py` |
| D03 | 角色 | realtime 可在执行中变更或终止「当下这条 gamescaling 指令」 | 「realtime 也可以在中途变更或终止执行，从而灵活的应对任务」 | 新增 instruction channel |
| D04 | 边界 | realtime **不能改任务**，只能改当下执行指令 | 「realtime 不能更改任务，只能更改这个当下 gamescaling 执行的指令」 | 任务变更走交棒 |
| D05 | 模型 | Omni 用阿里云托管版本（不自部署） | 「omni 用阿里云的，gamescaling 用云端自部署」 | 配置项 |
| D06 | 频率 | 画面以**连续视频流 5–10Hz** 喂入，不是 1Hz 快照 | 问答轮次：快系统#1（选项） | 截屏/推流模块 |
| D07 | 延迟 | **不追低延迟**，但延迟分布要像人（允许长尾） | 同上 | 打点指标定义 |
| D08 | 会话 | 每条意图新建一次 realtime 会话，结束即断 | 问答轮次：Omni 引擎（选项） | 会话管理器（新） |
| D09 | 上下文 | 会话内只保留当前意图的执行过程，结束即清 | 同上 | 同上 |
| D10 | 协议 | 输出用 **function call**，不用文本标记解析 | 「function call」 | tool schema |
| D11 | 工具 | realtime 仅 4 个受限工具：note_observation / request_handoff / ask_slow_reference / report_blocked | 问答轮次：工具集（多选） | tool 注册 |
| D12 | 权限 | realtime **不可读便利贴**（便利贴是给手模型的） | 多选未含 read_sticky；「快系统根本用不上这些数据」 | 权限表 |
| D13 | 断线 | realtime 断线 → 静默重连 + 预置台词撑场，观众无感 | 问答轮次：Omni 引擎（选项） | 重连器 + 台词池 |
| D14 | 冷启 | 接受每意图 1–3s 冷启，不做连接池（除非实测超标，见 §M-4） | 选项明示代价且被采纳 | 验收基线 |
| D15 | 输入 | 首帧随意图包一起给，快系统不自行抓帧 | 「快系统意图包＝意图+便利贴全量+当前画面（第一帧）」 | IntentPacket |
| D16 | 观察 | 途中观察用 note_observation 落事件，不打断执行 | 工具集选择 | timeline / session log |

**落地检查点**：会话管理器必须保证「同一时刻 ≤1 个活跃会话」，且旧会话走 `response.cancel` 而非"放弃等待"。

## B. 手模型（GameScaling）

要点：
- 手的输出规范**由训练决定、不可改**：一次 200ms = 6 步 × 33ms + 一次鼠标位移（屏幕千分比）+ 滚轮。
- 输入必须贴训练分布：三槽位系统提示词 + 当前帧 + 最近 5 帧历史 + 固定 user 文本 "current game screen"。
- 历史**跨调用保留**，但每意图开始 `policy.reset()`。
- 抢占只允许在**下一步边界**发生，不硬打断当前 chunk。

| 编号 | 主题 | 决策 | 依据 | 影响 |
|---|---|---|---|---|
| D17 | 输出 | 手输出原子键位流：200ms / 6×33ms / 每组 ≤4 键 | GameScaling README §5（训练规格） | `agent/gamescaling_action.py` |
| D18 | 鼠标 | 鼠标为相对位移（屏幕千分比 ±1000）+ 滚轮（±5 notch） | 同上 | 同上 |
| D19 | 模型 | 用 **GameScaling-2B-S3**（单卡，速度与质量折中） | 「2B-S3」；「我只有钱组一张卡」 | 部署清单 |
| D20 | 历史 | history_len = 5（与训练分布一致） | 问答轮次：手（选项） | `agent/motor.py` |
| D21 | 思考 | reasoning **默认开**，由模型自行决定何时思考 | 同上 | prefill `<think>` |
| D22 | 重置 | 每条意图开始调用一次 `policy.reset()` | 同上 | 编排层 |
| D23 | 历史写回 | 每步决策都要 `record(frame, action)`，否则手永远单帧无记忆 | 代码证据：`executor` 从不 record | `agent/executor.py` |
| D24 | 输入 | 手只吃截图（与 realtime 同一路视频流），不吃 UI 树 | 问答轮次：手（选项） | 采集层 |
| D25 | 提示词 | 三槽位提示词由**程序按模板拼**，慢系统只出 markdown 任务 | 问答轮次：交接（选项） | `agent/prompt_builder.py` |
| D26 | 提示词 | `**Game Rules**`/**Output Format**/**Explanation** 段头原样保留（含星号） | GameScaling README §2 | 模板 |
| D27 | 抢占 | 抢占在下一步边界生效（当前 chunk 走完再停） | 问答轮次：手（选项） | 执行循环 |
| D28 | 失败定性 | 解析失败（parsed=False / truncated）= **程序错误**，不是模型能力问题 | 「说明程序出现错误」 | 熔断链路 |
| D29 | 失败动作 | 冻结画面 → 落账 → 停推流 → 事故报告 → **退进程**，不热修重连 | 问答轮次：故障（选项） | 演练脚本 |
| D30 | 热切换 | 不做 checkpoint 热切换（只有一张卡） | 「我只有钱组一张卡，换什么 cp」 | 部署 |
| D31 | 延迟 | 手的单步延迟当**待测项**，先打 p50/p95 再决定是否双缓冲 | 「先打点测量，按实测决定流水线形态」 | 指标 |

**落地检查点**：手模型调用必须带「history 5 帧 + 固定 user 文本 + prefill」，三者缺一都会掉出训练分布（README §4 明确警告）。

## C. 慢系统与快慢互斥

要点（全系统最反直觉的一层，必须按原文理解）：
- **快慢互斥是故意的**：串行才不会互抢控制权；慢系统关掉 thinking 以压短画面冻结时间。
- 预算 **≤2s**；思考期画面**完全冻结**。
- 超预算的表现是画面中央显示「大肥鱼CPU烧了」——不隐藏、不假装。
- 慢系统输出「稍微规整的 markdown 文字」，与便利贴模板拼成给手的完整 prompt。
- 卡关判定是**主观**的：realtime 说「我卡住了」就算卡关。

| 编号 | 主题 | 决策 | 依据 | 影响 |
|---|---|---|---|---|
| D32 | 互斥 | 慢系统运行时 realtime 不运行；反之亦然 | 「realtime 运作时，慢系统不运行，快系统和慢系统同时只有一个会在运行」 | 状态机 |
| D33 | 互斥 | 串行是**故意设计**，为减少画面停止与互抢控制权 | 「是故意的，慢系统我故意加了让他断掉思考模式就是为了减少画面停止的时间」 | 不改 |
| D34 | 预算 | 慢系统单轮 ≤2s（只做轻量重规划） | 问答轮次：互斥（选项） | 超时配置 |
| D35 | 思考 | 默认关 thinking；卡关超过 N 次才允许 5–10s thinking | 同上（分级选项） | tier 选择 |
| D36 | 冻结 | 思考期画面完全冻结（改这条等于改设计，需重新拍板） | 「完全冻结（现状）」 | 渲染层 |
| D37 | 超时表现 | 超预算时画面中央显示「大肥鱼CPU烧了」 | 「直接画面中间放一个『大肥鱼CPU烧了』几个字」 | 贴图层 |
| D38 | 输出 | 慢系统输出「稍规整的 markdown 文字」，不强制 JSON | 「只需要稍微规整一些的 markdown 文字即可…再拼成完整结构化 prompt」 | 任务模板 |
| D39 | 模型 | 慢系统用 **deepseek flash** | 「deepseek flash」 | `agent/lithos.py` |
| D40 | 输入 | 输入 = 快系统回报 + 记忆检索 + 弹幕上下文 + 最近 30 轮意图与结果 + 全局约束 | 多选 +「N=30 轮」 | context builder |
| D41 | 取数 | 需要更多信息时**用 function call 自取**，不预塞 | 「剩余可以使用 function call 获取」 | tool 集 |
| D42 | 卡关 | 卡关由 realtime 主观判定（说「我卡住了」即交棒） | 「realtime 自己说『我卡住了』就交棒」 | 交棒触发 |
| D43 | 唤醒 | 唤醒事件含：卡关、新场景/新 UI、观众点单、任务落账、定时回顾 | 多选全选 | 事件总线 |
| D44 | 静止 | 「什么都不做」只在真空（加载、剧情演出）合法 | 「只有真空了才允许」 | 执行器策略 |
| D45 | 漂移 | 允许目标漂移，上限 ≤1 次/意图、≤10s | 「允许，但要可回收」 | 意图状态机 |
| D46 | 企划 | 「今天播什么/看点」由它据上轮进度+记忆自定，用户只审批 | 「它根据上一场进度 + 记忆自己定，我只审批」 | pre-flight |

**落地检查点**：互斥必须由状态机强制（断言），不能靠"调用顺序恰好如此"。

## D. 交棒与旁路子代理

要点：
- 交棒不是可选优化，而是**快系统的正常出口**：意图完成必须交棒。
- 回报只有两样：**一句话结论** + **见闻总结**（用户明确：状态变化、步数、残留动作都算见闻总结，不拆字段）。
- 旁路子代理两模式，都**看不到画面**；提前规划模式可开 thinking，且其结果有慢系统决策权。

| 编号 | 主题 | 决策 | 依据 | 影响 |
|---|---|---|---|---|
| D47 | 交棒 | 意图完成必须交棒（除非启用旁路"提前规划"） | 「快系统…全部使命就是完成这个意图，意图完成必须交棒」 | 状态机 |
| D48 | 交棒 | 意图失败立即回归慢系统重规划 | 「意图被判定失败后立即回归慢系统」 | 状态机 |
| D49 | 判定 | 完成判定只由 realtime 看画面决定，不做双签、不二次验收 | 「realtime 看画面判」+「不验，realtime 说了算」 | 单点判定 |
| D50 | 回报 | 载荷 = 一句话结论 + 见闻总结（markdown，尽量不丢关键信息） | 「你说的这些都叫见闻总结」 | HandoffReport |
| D51 | 回报 | 见闻总结按 02 §3.3 的**七段固定顺序**写：结论 / 我做了什么 / 看到了什么 / 听到了什么 / 我现在在哪·状态 / 还残留什么 / 值得记的 | 多选项（状态变化、新信息、残留动作）被用户并入「见闻总结」 | `02_schemas.md` §3.3 |
| D52 | 时限 | 意图不设硬时限，只看是否卡关 | 「不设硬时限，只看是否卡关」 | 无 TTL |
| D53 | 旁路 | 模式一「旁路建议」：快系统交当前状态换执行参考 | 用户原话 | 子代理 |
| D54 | 旁路 | 模式二「提前规划」：预测结果可预测时预规划下一轮慢系统内容，可开 thinking | 用户原话 | 子代理 |
| D55 | 旁路 | 两模式都**看不到画面**（只吃文本状态） | 「两种情况都不会看到画面」 | 输入约束 |
| D56 | 旁路 | 子代理权限低于快系统：不能插话/改任务；但提前规划产物有决策权，可直接跳过下一轮慢系统 | 用户原话 | 权限表 |
| D57 | 旁路 | 触发由快系统主动调用（ask_slow_reference） | 「快系统主动调用」 | tool 设计 |
| D58 | 旁路 | 结果只回给快系统，超时即丢弃，不阻塞主循环 | 设计新增（为满足 5–10Hz） | 异步投递 |

**落地检查点**：HandoffReport 必须是「必达」的——即使进程崩溃也要在落账目录留下半份，便于事后归因。

## E. 记忆与便利贴

要点：
- **Graphiti 只做长期记忆**；短期记忆只活在上下文里，不落库、不跨会话累积。
- 便利贴是**独立的快速模板层**：写进记忆的同时写进便利贴，用于快速拼出 `key_binding` + `game_rules`。
- 便利贴**慢系统独家写**；快系统与手模型只消费。
- 五层记忆全要：工作 / 情景 / 语义 / 程序性 / 社交。

| 编号 | 主题 | 决策 | 依据 | 影响 |

| D61 | 分层 | 五层全要：工作/情景/语义/程序性/社交 | 多选全选 | schema |

| D63 | 粒度 | 两层：一条 episode + 若干提炼原子事实 | 「两层」 | Graphiti episode+实体 |

## F. 主播人设与直播形态

要点：
- 复刻对象 **夜车Azuya**（bilibili 个人势虚拟UP主；绅士/下头、怪话、红温），但用户同时要「不要人设，就是个 AI 在玩」——**复刻说话方式与反应方式，不虚构世界观**。
- 单场 3–4 小时，**每场只播一个游戏**；排期表人工维护，**每次手动启动**。
- 不做自动切片、不做自动排期、不做声音表演。

## G. 时间轴与录播

要点：
- 只有一个时间基准：**本场开始以来的单调毫秒**；全系统共用，不允许第二次取时钟。
- 事件只有三类：`speech` / `l2d` / `viewer`，外加一条一直跟录的分片 mp4。（**播出侧**只有这三类；离线断言所需的控制事件不新增文件、共用同一 `t_ms`，见 02_schemas.md §6.2b 与 D101 备注。）
- TTS 时长未知：先按字数估算排布，音频回来再回填修正。

| 编号 | 主题 | 决策 | 依据 | 影响 |
|---|---|---|---|---|
| D100 | 时钟 | 基准 = 相对本场开始的单调毫秒 | 选项 | 全局 clock |
| D101 | 事件 | 播出侧事件仅 speech / l2d / viewer 三类（控制事件不新增文件、共用同一 `t_ms`，见 02 §6.2b） | 多选三项 | timeline schema |
| D102 | 录播 | 一直跟录，按固定 10 分钟切片 mp4 | 「按固定时长切（例如 10 分钟一片）」+「还要有一个一直跟录的、时间轴对得上的分片 mp4」 | 录制器 |
| D103 | 对齐 | 每片开头写 `start_ms` 与帧号，与时间轴同源 | 选项 | 分片索引 |
| D104 | TTS | 先按字数估时长排区间，回来再回填并顺延后续事件 | 「先按字数估时长排，TTS 回来后再修正区间」 | 说话调度 |
| D105 | 边界 | 只产出带时间轴的 JSON，合成/推流/立绘交给渲染组件 | 「先生成带时间轴的 json，剩下的留给渲染解决」 | 接口边界 |
| D106 | 索引 | 每意图首帧进意图索引，供复盘定位「这句话说的是哪一帧」 | 设计新增（基于 D15/D103） | 索引文件 |

**落地检查点**：TTS 回填只允许"向后顺延"，不允许回改已播出的事件时间（否则时间轴失去单调性）。

## H. 弹幕与观众

要点：
- 弹幕服务由其他项目提供，本系统**只消费不改**。
- 唯一消费者是**慢系统**；快系统不看弹幕，避免边打边被带节奏。
- 冲突原则：**执行优先**——弹幕记下，当前意图结束后再议。

## K. 决策之间的张力与解法

以下 8 组是本设计里**互相拉扯**的决策，实现时最容易各写各的、最后互相打脸：

| # | 冲突 | 解法 |
|---|---|---|
| 1 | D08 每意图重建会话 vs D07 延迟分布像人 | 冷启 1–3s 会被观众感知为"换人"。解法：交棒时**同时说一句过渡台词**（"那我先看看这边"），把冷启藏进这句话里；若实测冷启 >2s，改为单会话预热池（上限 1 个） |
| 2 | D32 串行互斥 vs D90 静默 ≤5s | 慢系统预算 2s 内一般不破 5s；一旦超时用 D37 贴图 + 预置「呃……」发呆台词填充，避免"静默违规" |
| 3 | D34 ≤2s vs D46 自定企划（需更长思考） | 企划分**开播前**做（不占直播时间）；thinking 分级只用于卡关（D35），不用于企划 |
| 4 | D69 便利贴按存档 vs D67 记忆全局+标签 | 便利贴是唯一"按存档"的层；跨存档复用只走 Graphiti 标签，不共享便利贴 |
| 5 | D76 记忆即全部已知 vs D64 每轮注入 | 注入必须过滤：只召回 `save_scope == 当前存档` 且 `observed_at != null` 的条目；其余即使相似度高分也丢弃 |
| 6 | D101 时间轴只三类事件 vs D106 需要意图索引 | 意图索引放独立的 `session_index.json`，不污染事件流 |
| 7 | D113 解析失败退进程 vs D85 3–4h 长播 | 退进程前必须落账 + 保存 `save_id` 与意图游标；重启后 pre-flight 提示"从上次中断处继续（人工确认）" |
| 8 | D110 实时扫弹幕 vs D109 执行优先 | 弹幕只在 PLANNING 阶段读；EXECUTING 阶段一律进缓冲，物理上不可读 |

## N. 实现前必须复核的 12 条断言

1. 同一时刻活跃 realtime 会话 ≤ 1；关闭时走 cancel（非放弃）。
2. 慢系统运行时不存在活跃 realtime 会话（状态机断言）。
3. 每步手模型调用都写回 history（length 恒 ≤5 且 >0）。
4. 每条意图开始都调用 `policy.reset()`，且不重复调用。
5. 手模型请求含：三槽位提示词 + 当前帧 + 5 历史帧 + 固定 user 文本 + prefill。
6. 时间轴事件 `t` 单调不减；跨意图不重置时钟。
7. 分片 `start_ms` 与时间轴同源（同一 clock 实例）。
8. 便利贴 ≤2048 字符，写入原子替换，超限拒绝并回滚。
9. 记忆召回结果经 `save_scope` + `observed_at` 过滤后才进 prompt。
10. HandoffReport 每个意图恰好一份（含 aborted）。
11. 解析失败路径能在 3 秒内冻结键位输出（先停手，再落账）。
12. 事故报告目录包含 D114 的五类留证，缺一不可。
