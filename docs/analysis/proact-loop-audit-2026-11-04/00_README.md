# ProAct 框架分析与「像真人一样玩游戏」能力审计

审计对象：BetterAGI 当前在跑的玩家 agent（`agent/tui.py` 单线程慢系统 + lithos 档位 + gamescaling motor + Omni 快旁白）
参考框架：ProAct（Proactive Real-time Agent，CVPR 2025 的 streaming 直播型 agent）
日期：2026-11-04　｜　取证时点：17:05–17:15　｜　性质：**只读审计，未改动任何产品代码**

---

## 0. 三句话结论

1. **ProAct 的骨架我们搭了，血没通。** 双系统、五维动机打分、意图总线、快系统旁白——名字全对得上、代码里都有对应物；但**驱动它们的链路（事件 → 打分 → 触发 → 动作 → 记忆回写）在真实运行里没有闭合**。三个最关键的零件是「假有」：意图总线是死代码、记忆只写不读、便签（scratchpad）不可达。
2. **当前 loop 的真问题不是「不会玩」，是「不会失败」。** 22 分钟真实会话里 **59%（290/491）轮次一个动作都没做**；同一个 `window not found` 失败 **152 次**、同一句「窗口一直没回来」重复 **75 遍**。缺的不是模型智力，是**失败归因 + 放弃 + 换招**。模型自己在第 10 步用 `learn_key` 补出了缺失键位（全场唯一一次真正学习）——能力在，触发机制不在。
3. **离「像真人」最远的不是动作精度，是「不做什么」。** 拟人度大量体现在**克制**：不直勾勾盯目标、会走错路再回头、看剧情不会秒按跳过、卡关会烦躁会换策略。我们现在的 loop 是**效率最大化**的（每轮必调工具、最短路径、失败就重试到底）——这在人类观感上恰恰是最不像人的。所以 P0-5 那条「设计哲学反向」比任何性能问题都重要：**系统默认「必须动」，而真人默认「可以不动」。**

## 2. 一页纸对照

### 2.1 当前 loop 的 P0 缺陷（5 条，逐条证据见 03 §2）

| # | 缺陷 | 玩家/观众能感知到的症状 |
| --- | --- | --- |
| **P0-1** | **Omni collect 无超时，且超时只「放弃」不「取消」** → 上一帧的响应串到下一帧 | 嘴在说上一秒的画面、动作与台词错位（串台） |
| **P0-2** | **手和嘴是两个模型且互不通信**（motor 选动作、Omni 出旁白，各自看各自的世界） | 嘴说「我往左走」，手却按了右 |
| **P0-3** | **全开环，没有任何端到端时效保证**（慢系统同步阻塞 `stream_complete`，一次 20s） | 想事时画面完全停住，「卡帧」感 |
| **P0-4** | **慢系统与记忆彻底脱钩**（recall 只在启动注入一次，写回也不进下游） | 每次开播都「第一次玩」，学过的全忘 |
| **P0-5** | **设计哲学反向：系统默认「必须动」，而不是「默认不动」**（每轮必调工具） | 乱按、抢剧情、发呆也不像人——**这条是拟人度的根** |

### 2.2 拟人化 9 层模型里最该先补的（04 §10 的 P0 行）

| 项 | 内容 | 为什么优先 |
| --- | --- | --- |
| **Q-3** | 显式 `wait` 工具 + 去掉「每轮必须推进」 | 成本极低，直接消灭「乱按」；是 P0-5 的落地形式 |
| **Q-2** | dialogue lock / 演出检测（看剧情不抢按键） | 剧情跳过率是观众最敏感的不像人信号 |
| **E-1** | 接记忆闭环（3 处传参） | 消「永远新手」 |
| **M-2** | 修 history 写回（1 行） | 消动作抖动 |
| **P0-1** | 修 Omni collect 超时 | 消串台 |

之后才是 P1 组：**D-5 意图总线接线 + 五维门控**、**R-1 反射层**、**P-4 多帧窗口**、**D-2/D-3 执行监控 + 慢 tick**、**F-1/F-2 失败分级与归因**。

## 3. 「像真人」的验收标准（不要用「感觉像」验收）

04 §11 定了 6 条，全部**可从现有 `_diag/agent-runs/*.jsonl` 算出**，不需要新埋点：

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 突发事件响应延迟 P50 | 1112ms（且高度恒定，P99 2252ms） | **< 250ms**（靠反射层），且要有长尾 |
| 同类动作 5s 内重复率 | 高（152 次同一 look） | **< 10%** |
| 剧情/演出场景跳过类按键比例 | 未测（loop 目标是「尽快推进」） | **< 2%** |
| 同位置停留 >8s 无进展 | 未测 | 逐月下降 |
| 跨会话知识复用（第二天提示词里已有的键位/规则条数） | ≈0 | 持续增长 |
| **5 人盲测（3 分钟录像）猜错率** | 未测 | **≥ 3/5** |

最后一条是唯一的「总验收」：**5 段 3 分钟录像混入 2 段真人，让人猜。猜错率不过半，前面所有优化都不算数。** 恒定延迟（1112ms ± 小方差）比慢延迟更像机器人——分布形状本身就是拟人信号。

## 4. 三个需要拍板的决策（05 §「需要立刻拍板的三个决策」）

1. **Graphiti 还是 local-json？** 主环境没装 `graphiti_core/fastembed`，而需求写「Graphiti 唯一长期记忆库」。装依赖（含 neo4j 运维）还是改文档承认 JSONL 为生产后端？**这个不定，M2 无法验收。**
2. **快系统模型？** 现在 Omni 是「1Hz 旁白 + 收手裁判」，REQ FR-3 却期望它「持续输出指令」。要么把 Omni 提升为真正的指令源（连续视频流 + 结构化输出），要么承认它只是旁白、指令权交回反射层 + 慢系统。**这决定 Phase 1 工作量。**
3. **「慢系统允许慢」到底多慢？** 现在默认 urgency 0.5 → 落 fast 档 30s 读超时，且 `stream_complete` 硬编码关 thinking。真要「想清楚再做」，需要开 thinking + 用真慢档模型（`base` 目前也是 deepseek-flash）。

## 5. 方法说明（为什么这份报告可信）

- **不拿 refactor 文档当现状。** `Docs/refactor/CURRENT_ARCHITECTURE.md` 与 `GAP_ANALYSIS.md` 比代码晚 7 天，且它们描述的 agent 层（tui/lithos/executor/gamescaling）全文 grep 只命中 1 处 / 0 处——描述的是 BetterGI + Lumine 那套旧双主体。本报告「现状」结论一律来自**代码行号 + 真实运行日志**。
- **区分「有 / 假有 / 无」。** 有类、有字段、有函数不算「有」；只有参与真实链路且**被读**才算。02 的矩阵逐项标了判定与证据行号，三个「假有」写在 02 §3。
- **用真实会话当第一证据。** 49 个真实 jsonl 里最长那条（491 轮 / 1322 秒 / 164 次工具失败）比任何单测更能说明问题。
- **测试绿 ≠ 能玩。** 203 个单测全绿，同时真实日志里 59% 轮次空转——不是矛盾，是覆盖面：测试测模块契约，没测「一个玩家能不能动」。缺端到端冒烟（起游戏 → 跑 60s → 断言有进展）。
